## 三、程式與資料執行方式

```text
店長／央廚／總公司瀏覽器或手機
              │
              ▼
      Vercel 上的 Next.js 系統
      ├─ App Router 頁面與元件
      ├─ Server Actions
      ├─ Route Handlers
      ├─ Excel／CSV 匯出
      ├─ 會議 PDF 產生
      └─ 單據 OCR
              │
              ▼
             Supabase
      ├─ Auth：登入與 Session
      ├─ PostgreSQL：營運資料
      ├─ Storage：照片與檔案
      └─ Realtime：同日結帳更新
```

一般店面與央廚操作帶著 Supabase 使用者 Session，資料庫以 RLS 限制資料範圍。跨表或總公司操作由 Next.js Server Action／Route Handler 先驗證登入者與細分權限，再於伺服器端執行。`SUPABASE_SERVICE_ROLE_KEY` 僅存在伺服器環境，不會送到瀏覽器。

## 四、登入與權限實作

1. 使用者在登入頁輸入公司帳號與密碼。
2. 系統把公司帳號轉為內部 Auth Email：`帳號@liang-ping.com`。
3. Supabase Auth 驗證後建立 Session。
4. `auth.users.id` 對應 `public.user_profiles.user_id`。
5. `user_profiles` 的角色、店家清單與細分權限決定可進入的頁面與可執行的操作。

目前權限不是只靠畫面隱藏按鈕；頁面、Server Action 與資料庫 RLS 分別檢查登入狀態、角色、店家範圍或細分權限。

工程師檢視帳號的現行設定：

| 權限範圍 | 設定 |
| --- | --- |
| 身分 | 顧問／系統整合工程師 |
| 營運功能 | 可進入並編輯店家與央廚設定、品項、收據設定、央廚單價、帳務審核及報表 |

## 五、已完成的功能

### 店面端

- 每日營業額輸入：現場、Uber Eats、foodpanda、台灣 Pay、線上點餐、店內外送等通路
- 每日結帳、現金清點、應繳金額與差異計算
- 單據照片上傳、品項與金額輸入、備註與 OCR
- 廠商、收據類別與品項管理連動
- 歷史帳目、退回帳目提醒與重新送出
- 營運統計與會議報告

### 央廚端

- 每日帳務與採購支出
- 體系內店家叫貨、體系外店家銷售
- 店面輸入與央廚輸入交叉核對
- 店面上傳配送單照片同步與差異顯示
- 單據類型、退稅、稅外加、品項與廠商分類
- 央廚單價與歷史紀錄

### 總公司端

- 店面與央廚帳目審核、退回與逾期提醒
- 單據照片逐張核對
- 店家與央廚對帳
- 月營業額、支出、成本率、收據分類與細項統計
- 店家、帳號、品項、收據分類與權限管理
- Excel／CSV 匯出、Google 試算表功能
- 操作軌跡

### 會議報告

- 兩期營業額、現場、外送平台、線上點餐與店內外送比較
- Google 評論、客訴、照片與個別同仁分析
- 上次改善追蹤與本次問題提案
- 行動項目跨次會議帶回
- 伺服器端產生 PDF

### 照片處理

1. 使用者在瀏覽器選取照片。
2. 圖片先在前端壓縮，再上傳 Supabase Storage。
3. 資料庫保存檔案位置與店家、日期、單據資料的關聯。
4. 列表先載入縮圖，核對時再載入較高畫質版本。
5. OCR Route Handler 驗證照片來源後交給 Gemini 辨識。

| Storage bucket | 內容 | 狀態 |
| --- | --- | --- |
| `receipts` | 收據與配送單照片 | 公開 |
| `meeting-reports` | 會議評論、客訴、提案照片 | 公開 |
| `excel-templates` | Excel 範本與欄位設定 | 私有 |
| `menu-videos` | 菜單教學影片 | 私有 |

## 八、Excel、PDF 與第三方服務

- ExcelJS 讀取範本與產生店面、央廚、成本等報表。
- Puppeteer Core 搭配 Vercel Chromium，在伺服器端把會議報告頁面輸出為 PDF。
- Google Gemini API 接收可信的單據照片，回傳單據類型、金額與辨識內容。
- Google Service Account 用於系統內的 Google 試算表功能。
- Service Worker 提供 PWA 安裝與部分靜態資源快取。

## 九、部署與環境建立方式

### 程式部署

1. 原始碼以 Git 管理，正式分支為 `main`。
2. `npm test` 執行測試。
3. `npm run build` 執行測試與 Next.js 正式建置。
4. GitHub `main` 更新後，Vercel 進行建置與部署。
5. 正式版本可由 `/api/version` 檢查部署識別。

### 資料庫部署

1. Schema 變更以新的 SQL migration 加入 `supabase/migrations/`。
2. Migration 套用到 Supabase PostgreSQL。
3. 依新 Schema 更新程式並部署 Vercel。
4. 權限或資料調整保留在 migration、Server Action 或稽核紀錄中。

### 正式環境變數名稱

| 名稱 | 用途 |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase 專案網址 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 瀏覽器 Supabase Client；資料權限由 RLS 控制 |
| `SUPABASE_SERVICE_ROLE_KEY` | 伺服器限定的管理金鑰 |
| `GOOGLE_GEMINI_API_KEY` | 單據 OCR |
| `GOOGLE_SERVICE_ACCOUNT_CREDENTIALS` | Google 試算表功能 |

正式環境變數的值保存在部署環境，不寫入 Git。Firebase 遷移相關變數目前未啟用。
